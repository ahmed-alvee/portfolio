Lessons from using an LLM to clean up messy clinic data

Written from work using Claude through Amazon Bedrock.

I built an AI clean-up pipeline with LangGraph, Claude on Amazon Bedrock, Pydantic and ChromaDB. Per-submission time improved from about 1 hour to 6-10 minutes, including human review, for 30+ clinics. My first version had at least one wrong attribute in 70% of individual records. The final pipeline got 99% of the data submitted to the live database.

The problem

Clinics sent patient submissions as CSV and Excel files. Every vendor used its own column names, and each customer had its own list of package names. A person cleaned each submission by hand, which took about an hour.

I had to get an LLM to turn those files into clean, structured output a reviewer could trust. The model had to follow instructions closely, stay within cost, and fit the work inside the context window of the models available at the time.

The first version failed

These were live medical records. In my view, it is better to fail early than to be sorry later, so the pipeline had to fail gracefully before it put in wrong or half-baked data.

My first version gave the LLM only a system prompt and the file paths. 70% of individual records had at least one attribute wrong. The root cause was that the LLM got no feedback on whether its output was correct. In my view, a human in that loop would have defeated the purpose of an agentic workflow. The feedback had to come from the pipeline itself.

Six lessons

1. Start with the raw file and read what the model does. I began with the file and the expected output in the system prompt and the first message, and watched the patterns. Testing across models showed that Claude Sonnet followed instructions best, so I used it.

2. If the model writes the same script every turn, make it a tool. Given a CSV or an Excel file, the model wrote a Python script from scratch each time. I turned those scripts into tools: look at the data, map column names, count records, write a new output CSV and track progress. The model then spent its effort on transforming the data.

3. Search for reference data. The list of package names was long and different for each customer. I gave the model a ChromaDB vector search to find the closest match. Each customer had about 100 accepted values, out of 500+ across customers, and giving the model all of them would only work with a large context window. So at the start of each run I loaded only that customer's values into ChromaDB, with Cohere embeddings. The model searched for the closest matches and checked whether the input value was on the accepted list. A vendor might send "Silver Male" when the exact name was "Silver Package Male". If the vendor sent only "Silver Package", the model used the patient's gender to choose the Male or the Female package.

4. Work in steps, because of the context limit, context rot and cost. The context window of the models at the time was smaller than it is now. Feeding the whole file at once also cost more, and the model got worse as the context grew. LangGraph stages divided the data and spawned multiple LLMs to work in parallel, with a supervisor agent that had visibility over them all. The flow moved in steps:

extract the required fields (test name, value, units, abnormal flag)
  -> structure them into a JSON schema
  -> fetch parameter names through an internal API
  -> map test names to internal names and codes
  -> call the validation endpoint
  -> read the feedback and correct
  -> validate again
  -> write the cleaned file

5. Check the output outside the model. The validation endpoint used Pydantic, which also gave the model the JSON schema for its tools. Its error messages were very specific. If only the phone number was wrong, the error pointed to the phone number and said why, and the model corrected only that data point. It checked that patient identifiers were in capitals, that phone numbers had the country code separate from the number and were valid, and that emails were valid. One Pydantic model handled many records. In testing and on live submissions, when the first row passed, the rows after it passed the same checks. The model processed 10 to 20 records at a time. I reached this flow after many tests.

6. Keep a person in the loop. The model did not submit anything. It produced a cleaned file, and a human reviewer checked each finished file and submitted it.

I also built and tested a public endpoint that connected vendors to the LLM. I did not release it: it needed more testing, and its forecast cost was a factor.

The outcome

Per-submission time improved from about 1 hour to 6-10 minutes, including human review, for 30+ clinics. The first version had at least one wrong attribute in 70% of individual records. The final pipeline got 99% of the data submitted to the live database. The other 1% was incomplete data from the customer or data we could not transform into a complete record. Building the workflow from start to finish took about 2 months.
